好友私信功能设计报告

相互关注才能聊天 · 新粉丝提示 · Web 与 Android 双端方案

一、目标与结论

在现有「关注 / 好友动态」基础上，增加一套轻量、可控的私信能力，让同学之间可以围绕运动互相约跑、打卡提醒，同时避免陌生人骚扰。

  • 核心规则：只有相互关注的人才能互相发消息，单向关注只能看动态，不能发私信。
  • 关注提示：有人关注你时，在消息入口产生红点，并生成一条「XX 关注了你」通知，可直接回关或进入聊天。
  • 推荐实现：一期用数据库 + HTTP 轮询，不引入 WebSocket；二期再考虑 SSE 推送。
  • 范围：本期只做文本消息；图片、语音、表情包放到后续版本。
设计原则：规则简单、后端强校验、前端弱提示。所有「能不能发」的判断都在服务端完成，客户端只负责展示状态，避免被绕过。

二、现状与可复用能力

已有能力现状本次如何复用
关注关系 follows(follower_id, followee_id, created_at)，两人唯一 直接用于判断是否互相关注、查询会话对象
排行榜关注按钮 Web 与 App 都已支持关注 / 取消关注 复用关注动作，关注时写入通知
好友动态 /api/follows、/api/follows/feed 动态行增加「发消息」入口（仅互关时显示）
JWT 鉴权 所有接口从令牌取用户，不信任前端 userId 私信接口同样从令牌取发送者
用户资料 昵称、性别（决定默认头像） 会话列表与聊天气泡显示头像、昵称

三、功能范围

MVP一期必须

  • 相互关注校验，非互关不可发消息
  • 消息中心入口 + 未读红点
  • 会话列表（按最后一条消息时间排序）
  • 聊天页：文本发送、历史消息、时间分组
  • 已读状态（对方打开会话即标记已读）
  • 新粉丝通知「XX 关注了你」，可回关
  • 消息频率限制与长度限制

二期后续迭代

  • SSE 实时推送，替代轮询
  • 图片消息、运动卡片分享
  • 消息撤回（2 分钟内）
  • 拉黑 / 举报
  • 会话置顶、免打扰
  • 未读数角标同步到桌面图标（App）

四、核心业务规则

4.1 能否发消息

服务端每次发送前校验：A 关注了 B 且 B 关注了 A，且不是自己。任一条件不满足返回 403，提示「相互关注后才能聊天」。

A 打开 B 的资料→ 是否互相关注→ 是：显示「发消息」 / 否：显示「关注 TA」

4.2 取消关注后的处理

  • 历史消息保留可见，但输入框置灰并提示「相互关注后才能继续聊天」。
  • 会话仍留在列表，避免用户误以为消息丢失；重新互关后自动恢复发送能力。
  • 若选择「删除会话」，只删除自己侧的可见记录（软删除字段），不影响对方。

4.3 防骚扰限制

  • 单条消息长度 1–500 字，去掉首尾空白后不能为空。
  • 同一会话 10 秒内最多 5 条，超限返回 429。
  • 非互关状态不允许发起新会话，从源头阻断陌生人私信。
  • 一期不做黑名单，但保留 blocked 字段的扩展位。

五、数据模型

5.1 messages（私信）

CREATE TABLE messages (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  sender_id CHAR(36) NOT NULL,
  receiver_id CHAR(36) NOT NULL,
  content VARCHAR(500) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  read_at DATETIME NULL,
  sender_deleted TINYINT NOT NULL DEFAULT 0,
  receiver_deleted TINYINT NOT NULL DEFAULT 0,
  KEY idx_messages_pair_time (sender_id, receiver_id, created_at),
  KEY idx_messages_receiver_unread (receiver_id, read_at),
  CONSTRAINT fk_messages_sender FOREIGN KEY (sender_id) REFERENCES users (id) ON DELETE CASCADE,
  CONSTRAINT fk_messages_receiver FOREIGN KEY (receiver_id) REFERENCES users (id) ON DELETE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

说明：不单独建 conversations 表，会话列表通过「按对方聚合 + 取最后一条」查询生成，数据量小、实现简单。

5.2 notifications（关注提示与系统通知）

CREATE TABLE notifications (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id CHAR(36) NOT NULL,        -- 接收者
  actor_id CHAR(36) NULL,           -- 触发者，如关注你的人
  type VARCHAR(16) NOT NULL,        -- follow / message / system
  content VARCHAR(200) NULL,
  read_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_notifications_user (user_id, read_at, created_at),
  CONSTRAINT fk_notifications_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

关注成功时插入一条 type='follow' 通知；取消关注不删除历史通知，但可标记失效。消息通知可只依赖未读数，不必每条消息都写 notifications，避免表膨胀。

5.3 数据量估算

项目估算说明
单条消息约 0.5 KB含索引开销
1000 用户 / 每天 2000 条约 1 MB / 天一年 365 MB，MySQL 单机完全可承受
会话查询走 idx_messages_pair_time按对方 + 时间倒序，分页取 30 条

六、接口设计

方法路径说明关键返回
GET/api/messages/unread 未读汇总 { unread: 3, followers: 1 }
GET/api/messages/conversations 会话列表 对方 id / 昵称 / 性别 / 最后一条 / 时间 / 未读数
GET/api/messages?userId=&before=&limit= 与某人的历史消息 按时间倒序分页，before 传最小 id 或时间
POST/api/messages 发送消息 { receiverId, content } → 新消息 + 对方是否互关
PUT/api/messages/read 打开会话时标记已读 { userId } → 将对方发给我的未读全部置为已读
GET/api/notifications 通知列表（关注提示） type / actor 昵称 / 时间 / 是否已读
PUT/api/notifications/read 标记通知已读 { id } 或全部已读
GET/api/users/{id}/card 用户资料卡（互关状态） 昵称 / 性别 / 本周时长 / mutual 布尔
发送消息返回体中带 mutual 字段，客户端可即时刷新输入框状态；服务端始终以数据库为准。

七、交互与页面

7.1 入口

  • Web：底部导航「我的」页新增「消息」入口；排行榜与好友动态行内「发消息」按钮（仅互关显示）。
  • App：「我的」页新增「消息」入口；排行榜用户卡片与好友动态头像可点击进入聊天；顶部消息图标带未读红点。
  • 关注提示：消息入口显示小红点；进入消息页顶部展示「XX 关注了你」，右侧提供「回关」按钮。

7.2 页面结构

消息中心→ 会话列表 / 新粉丝→ 聊天页→ 对方资料卡
  • 消息中心：顶部「新粉丝」横条（关注提示），下方会话列表；空状态引导去排行榜关注同学。
  • 会话列表：头像、昵称、最后一条消息摘要、时间、未读数字；左滑或长按删除会话。
  • 聊天页：对方昵称与互关状态；气泡左右分布，时间超过 5 分钟插入时间分割；底部输入框 + 发送按钮；非互关时输入框禁用并提示。
  • 资料卡：昵称、头像、本周时长、关注状态、发消息按钮。

7.3 关键状态

状态表现
相互关注输入框可用，发送按钮高亮
单向关注 / 未关注输入框置灰，提示「相互关注后才能聊天」，提供「关注 TA」按钮
对方取消关注历史消息保留，输入框禁用；顶部提示「对方已取消关注」
发送失败消息气泡显示红色感叹号，点击重试
未读消息入口红点 + 会话行未读数

八、实时性方案

方案优点缺点建议
HTTP 轮询 实现最简单，无需长连接与网关改造；Spring 直接支持 有延迟、产生空请求 一期采用会话页 5 秒、消息入口 20 秒，页面不可见时暂停
SSE 服务端单向推送，实现成本低于 WebSocket；Spring MVC 原生支持 需要处理断线重连、Caddy 长连接超时；App 端需额外接入 二期Web 先上，App 仍可轮询
WebSocket 全双工、延迟最低 改造最大，需要连接管理与鉴权 暂不采用
轮询注意：仅在聊天页可见时轮询；使用 document.visibilityState 与 App 的 onResume/onPause 控制，避免后台耗电与无效请求。

九、关注提示设计

  • 触发：关注接口成功后，向被关注者写入 notifications(type='follow')；重复关注不重复写。
  • 展示：消息入口红点；消息页顶部「新粉丝」卡片，显示「XX 关注了你 · 2 小时前」，提供「回关」与「发消息」。
  • 消除：进入新粉丝列表或点击「回关」后，将对应通知置为已读，红点消失。
  • 限制：同一人反复关注/取关只保留一条最新通知，避免刷屏。

十、安全与隐私

  • 所有接口从 JWT 取当前用户，禁止信任请求体中的发送者 id。
  • 互相关注校验在服务端执行，前端隐藏入口只是体验优化。
  • 消息内容做长度与空白校验；输出时统一转义，防止 XSS（Web 端用文本节点渲染，不使用 v-html）。
  • 不做端到端加密（当前场景无必要），但数据库中不存储任何敏感信息。
  • 用户注销/清空数据时，级联删除其消息与通知（外键 ON DELETE CASCADE）。
  • 后续可增加举报与拉黑；数据模型已为 blocked 预留扩展位。

十一、实施计划

阶段内容产出
阶段 1 数据库迁移、消息与通知接口、互关校验 schema.sql、Controller/Service/Mapper、接口自测
阶段 2 Web 消息中心、会话列表、聊天页、关注通知 /messages、/messages/:userId 页面与未读红点
阶段 3 Android 消息入口、会话列表、聊天页 MessagesActivity、ChatActivity、轮询刷新
阶段 4 未读角标、轮询优化、异常与空状态打磨 双端体验对齐，验收通过

每阶段完成后独立构建与部署，消息功能不影响现有打卡、排行、轨迹链路。

十二、验收标准

  1. 未互相关注时，双方都无法发送消息，接口返回明确提示。
  2. 互相关注后，Web 与 App 均可正常收发文本消息，刷新后消息不丢失。
  3. 对方打开会话后，未读数归零；发送方可在会话列表看到最新消息摘要。
  4. 被关注者能看到「XX 关注了你」提示，点击回关后可立即聊天。
  5. 取消关注后，历史消息仍可查看，但无法继续发送。
  6. 10 秒内连续发送超过 5 条会被限流，提示稍后再试。
  7. 会话列表按最后消息时间倒序，空状态有引导文案。
风险点：双端同时上线周期较长。建议先完成 Web 端与后端接口，App 端随后跟进；轮询方案对服务器压力可控，但需在用户量上升后评估是否切换 SSE。
